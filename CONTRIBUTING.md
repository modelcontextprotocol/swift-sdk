# Contributing

Thank you for your interest in contributing to the MCP Swift SDK! This guide covers how to build,
test and change the SDK, and how issues and pull requests are handled.
Background: [design/design.md](design/design.md). Policies: [VERSIONING.md](VERSIONING.md),
[DEPENDENCY_POLICY.md](DEPENDENCY_POLICY.md). Security reports: [SECURITY.md](SECURITY.md).

If you work with an AI coding agent, also point it at [AGENTS.md](AGENTS.md). That file covers the
technical conventions in this codebase: message definitions, concurrency, platform gates, and test
patterns.

## AI Policy

The MCP community allows the use of AI assistant tooling for contributions. Before using AI agents,
please review [the MCP AI Policy](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/AI_POLICY.md)
to understand the guidelines and responsibilities for such contributions. In short:

- **Disclose it.** State in the PR description or issue that AI was used, and to what extent.
- **Own it.** You must understand the change and be able to explain it in your own words. When a
  maintainer asks a question, the answer should come from you, not be pasted from a chat window.
- **Keep a human in the loop.** Don't let agents open PRs, file issues, or post comments without a
  person reviewing the output first.

## Before You Start

Open an issue and agree on the approach before writing code for:

- New public APIs, or changes to existing public API shapes
- Architectural changes, such as the `Transport` protocol or the `Client` / `Server` actors
- Changes that cut across many files or modules
- Behavior not covered by the MCP specification. These need a
  [Specification Enhancement Proposal (SEP)](https://modelcontextprotocol.io/seps)
  first.

## Development setup

- Swift 6.1 or later. On macOS use the toolchain of Xcode 16.3 or later.
- Linux: a Swift 6.1 toolchain and `libcurl4-openssl-dev` (FoundationNetworking), or
  `scripts/ci-linux.sh` on a Mac (see [CI and Linux](#ci-and-linux)).
- Conformance runs: Node.js (CI uses 22) and access to the public npm registry.

With a private npm registry configured, use the public one:

```sh
export npm_config_registry=https://registry.npmjs.org
```

## Build and test

```sh
swift build                              # library, fixtures, examples, snippets
swift test                               # MCPTests and SnippetTests
swift test --filter ClientStatelessTests # one suite
swift build --product mcp-everything-server
swift build --product mcp-everything-client

BIN="$(swift build --show-bin-path)"
"$BIN/HelloClient" "$BIN/HelloServer"    # stdio smoke test, as in CI

swift package generate-documentation --target MCP --warnings-as-errors
swift scripts/doc-coverage.swift         # every public declaration has a doc comment
swift scripts/weave.swift --check
```

Tests use Swift Testing (`import Testing`, `@Suite`, `@Test`). Most run over `InMemoryTransport`
or `Tests/MCPTests/Helpers/MockTransport.swift`. Golden wire tests use `expectWire` from
`Tests/MCPTests/Helpers/WireExchange.swift`. HTTP client tests share one `MockURLProtocol`, so
they belong to the serialized `HTTP Client Transport Tests` suite.

## Conformance

`scripts/run-conformance.sh` runs `@modelcontextprotocol/conformance` (pinned to
`0.2.0-alpha.11`) against `mcp-everything-server` and `mcp-everything-client`. Details:
[conformance/README.md](conformance/README.md).

| Leg | Command | Baseline |
|---|---|---|
| 2025-11-25 wire | `scripts/run-conformance.sh --spec-version 2025-11-25` | `conformance/baseline.2025-11-25.yml` |
| 2026-07-28 wire | `scripts/run-conformance.sh --spec-version 2026-07-28` | `conformance/baseline.2026-07-28.yml` |
| default wire, all scenarios including extensions | `scripts/run-conformance.sh` | `conformance/baseline.yml` |
| tier score | `scripts/run-conformance.sh --requirements <rev>` | none; any scored failure fails |

Options: `--mode client|server|both` (default `both`), `--bin-path "$(swift build --show-bin-path)"`
(skip the build), `--port` (default 3001), `--output-dir` (default `.build/conformance`),
`--solo-attempts <n>` (re-run unexpected failures alone; default 1), `--update-baseline`.

Rules:

- Baselines are generated by `scripts/conformance-baseline.mjs`. Do not edit them by hand.
- A run fails on an unexpected failure (not in the baseline) and on a stale entry (in the
  baseline but passing). `WARNING` counts as a failure.
- A change that fixes or breaks a scenario regenerates the affected baseline in the same change:

  ```sh
  scripts/run-conformance.sh --spec-version 2026-07-28 --update-baseline
  ```

- Entries should only go down. A pull request that adds entries explains why.
- The fixtures use the public API only. Do not special-case a scenario in a fixture; fix the SDK.
- CI runs every leg and tier score, on macOS and Linux, on pushes and pull requests to `main`
  (see [CI and Linux](#ci-and-linux)).

## Interop

`scripts/run-interop.sh` runs the Swift SDK's clients and servers against pinned releases of the
Go and Python SDKs (needs Go and `uv`). Run it after protocol or transport changes, and record a
changed outcome with `--update-results`. `--check` fails when the results differ from
`interop/RESULTS.md`; CI runs it that way. Details: [interop/README.md](interop/README.md).

## CI and Linux

The CI jobs are listed once, in `scripts/ci/jobs`; each is a script in `scripts/ci/`.
`scripts/ci/run-jobs.sh [<id-regex>...]` runs them, and GitHub Actions
(`.github/workflows/ci.yml`) calls it. On macOS run it directly:

```sh
scripts/ci/run-jobs.sh                        # every job
scripts/ci/run-jobs.sh 'conformance-.*' interop
```

On a Mac, `scripts/ci-linux.sh` runs the same jobs on Linux in a container, in a RHEL UBI 9
Swift image (Apple silicon, macOS 26 or later):

```sh
brew install container && container system start
scripts/ci-linux.sh all                       # every job, then a summary
scripts/ci-linux.sh conformance-2026-07-28-client
scripts/ci-linux.sh conformance --spec-version 2025-11-25 --mode client   # any script and flags
scripts/ci-linux.sh --shell                   # a shell in the container, at /w
scripts/ci-linux.sh --image swift:6.1-noble all       # Ubuntu 24.04
scripts/ci-linux.sh -- swift test --filter StatelessHTTPTests   # any command, at /w
```

The container gets a copy of the working tree, including uncommitted changes. Builds persist
in a named volume and package caches in `~/Library/Caches/mcp-swift-sdk-ci`, so reruns are
incremental; results land in `.build/linux/<image>-<arch>/`. `--platform linux/amd64` runs
x86_64 under emulation. `--update-baseline` and `--update-results` copy their output back into
the tree.

A fast loop for one branch at a time, for example a worktree of a stacked branch: build a
reference volume once, then give each worktree a session of its own, seeded from it. The
session's container stays up, so a rerun only re-syncs the tree and builds what changed:

```sh
scripts/ci-linux.sh --build-volume mcp-ci-ref-arm64 -- swift build --build-tests   # once
scripts/ci-linux.sh --source ../wt-p5 --build-volume mcp-ci-wt-p5 --seed-from mcp-ci-ref-arm64 \
    --session wt-p5 -- bash -c 'swift build --build-tests && swift test --skip-build --filter X'
scripts/ci-linux.sh --stop-session wt-p5   # the volume stays, warm, for the next session
```

A volume can be attached to one running container at a time, so sessions that run in parallel
need their own `--build-volume` (and a reference volume cannot seed while a session holds it).
A run with a `--build-volume` other than the default puts its results in `.build/linux/<volume>/`.

Conformance baselines and `interop/RESULTS.md` are shared by macOS and Linux, and every job
gates on both. A job that fails on Linux for a known reason can be marked `advisory` in
`scripts/ci/jobs` (it runs and reports without failing CI) with the reason in
[design/linux.md](design/linux.md); none is today. When an advisory job passes, `run-jobs.sh`
says so; mark it `gate`.

### Fuzzing

`fuzz/` is a separate package of libFuzzer targets: wire decoding, the SSE parser, and both HTTP
server transports. The HTTP targets also check that each input's server is released. libFuzzer
ships only with the Linux toolchain, so run it in the container:

```sh
scripts/ci-linux.sh fuzz 300                  # five minutes per target
```

An input that crashes is saved in `.build/linux/<image>-<arch>/fuzz/artifacts/`; add it to
`fuzz/corpus/<target>/` with the fix.

## Documentation

| What | Where | How |
|---|---|---|
| Guides | `docs/src/*.src.md` | edit the source, then `swift scripts/weave.swift` |
| Repository README | `README.src.md` | edit the source, then `swift scripts/weave.swift` |
| Code in guides | `Examples/Snippets/<Area>/*.swift` | between `// snippet: <name>` and `// endsnippet`; included with `%include <path> <name>` |
| API reference | doc comments in `Sources/MCP` | DocC |
| Design | `design/*.md` | edit directly |
| Process | root `*.md` | edit directly |

- `docs/*.md` and `README.md` are generated. Never edit them; edit `docs/src/*.src.md` or
  `README.src.md` and run the weave script.
  Commit the source and the output together.
- Snippets are compiled by `swift build` and tested by `SnippetTests`, so they cannot drift.
- CI runs `swift scripts/weave.swift --check`. It fails when `docs/*.md` or `README.md` is stale, when a
  relative link or heading anchor in `docs/` does not resolve, or when a `##` section of
  `protocol.md`, `server.md` or `client.md` is not linked from `docs/README.md`.
- CI builds DocC with `--warnings-as-errors`. A broken symbol link fails the build.
- CI runs `swift scripts/doc-coverage.swift`, which lists every public declaration in
  `Sources/MCP` without a `///` comment.
- A change in behavior updates the guide, the design note and, for breaking changes,
  [docs/migration.md](docs/migration.md).

Guides: [docs/README.md](docs/README.md), [docs/protocol.md](docs/protocol.md),
[docs/server.md](docs/server.md), [docs/client.md](docs/client.md).

## Coding Style

Follow [the Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/),
and match the style of the surrounding code. [AGENTS.md](AGENTS.md#core-development-principles) has
more rules and examples for message definitions, concurrency, platform gates, and tests.

- **Formatting**: use 4-space indentation. `.vscode/settings.json` enables format-on-save, so don't
  commit unrelated formatting changes. Check your diff for reformatted lines outside your change.
- **Imports**: match the file you're editing. Some files import specific Foundation symbols
  (`import struct Foundation.Data`), and others use `import Foundation`. List `import Logging`
  first.
- **No file headers**: source files start with imports, with no license or copyright banner.
- **Doc comments**: document every `public` symbol with `///`. Keep them terse: a one-line
  summary, then facts (wire behavior, error codes, the revision a member applies to), with DocC
  callouts (`- Parameters:`, `- Returns:`, `- Throws:`, `- SeeAlso:`, `- Important:`). Use
  ` ``Symbol`` ` links only for symbols that resolve, because CI fails on broken links. Use
  single backticks for method names, header names, and other literals. Code samples in doc comments
  are not compiled, so check them against the real API.
- **Organization**: separate a type from its extensions with `// MARK: -`, and label sections with
  `// MARK: - Name`. Put protocol conformances in separate extensions where the file already does.
- **Codable**: use `private enum CodingKeys: String, CodingKey`. Encode optional fields with
  `encodeIfPresent`.
- **Errors**: throw `MCPError` from protocol and transport code: `.invalidParams` for bad input,
  `.methodNotFound` for unsupported capabilities, `.invalidRequest` for lifecycle violations, and
  `.internalError` otherwise, with a short message. OAuth failures use `OAuthAuthorizationError`.
  Don't swallow errors silently. If an error is intentionally ignored, log it and explain why.
- **Logging**: use the transport's swift-log `Logger`. Labels follow `mcp.transport.<kind>`, and the
  default logger is a no-op. Use `trace` for per-message events, `debug` for lifecycle events,
  `warning` for unexpected input, and `error` for failures. Put structured values in `metadata:`.
  Never log tokens, secrets, or authorization headers.
- **Security-sensitive code** (`Authorization/`, `HTTPRequestValidation.swift`): validate URLs and
  inputs with the existing validators. Keep secrets out of errors and logs, and add tests for each
  rejected input.
- Code that differs per protocol revision reads `ProtocolProfile` flags
  (`Version.profile(for:)`). Do not compare version strings.
- A new protocol method is a new `Method` type. Keep wire names (`_meta`, `ttlMs`).
- New public types are `Sendable`. The `MCP` target builds with strict concurrency.
- Wire changes get a golden test (`expectWire`).

## Issues and triage

File issues in the repository's issue tracker (`modelcontextprotocol/swift-sdk` on GitHub).
Include what you did, what you saw, what you expected, the SDK commit or version, the Swift
version (`swift --version`), the platform, and the protocol version of the connection.

### Labels

One type label per issue:

| Label | Use |
|---|---|
| `bug` | the SDK does not do what its documentation or the specification says |
| `enhancement` | new API or behavior |
| `spec-compliance` | a gap between the SDK and a specification revision or SEP |
| `conformance` | a conformance scenario fails or a baseline entry exists |
| `documentation` | guides, design notes, doc comments |
| `question` | usage questions |

### Priorities

| Priority | Meaning | First response | Target |
|---|---|---|---|
| `P0` | core functionality broken (connection, message exchange, tools, resources, prompts) or a high-severity security issue | 1 business day | fix within 7 days |
| `P1` | significant bug that affects many users, or a regression | 2 business days | next release |
| `P2` | moderate bug or valuable feature | 5 business days | as capacity allows |
| `P3` | minor issue or rare edge case | 10 business days | opportunistic |

### Process

- The repository maintainers triage. One maintainer per week is on triage duty and gives every
  new issue a type and a priority, or asks for missing information, within two business days.
- Security issues are not triaged in public; see [SECURITY.md](SECURITY.md).
- Spec changes: each SEP in a new specification revision gets a `spec-compliance` issue with the
  SEP number in the title. [ROADMAP.md](ROADMAP.md) lists implemented and deferred SEPs. A new
  conformance harness version is adopted in its own pull request that updates the pin and
  regenerates the baselines.
- An issue waiting for the reporter for 14 days may be closed. It can be reopened.

## Pull requests

- Link the issue. Nontrivial changes without an issue start with one (see
  [Before You Start](#before-you-start)).
- Keep the change to one topic. Do not mix refactoring with behavior changes.
- Required before review:
  - `swift build` and `swift test` pass.
  - The conformance legs pass; baselines are regenerated in the same change when results change.
  - `swift scripts/weave.swift --check` passes; DocC builds with `--warnings-as-errors`.
  - Tests cover the change, including wire tests for wire changes.
  - Docs are updated (guide, design note, ROADMAP for SEP status).
- Breaking changes ([VERSIONING.md](VERSIONING.md#breaking-changes)) say so in the description
  and update [docs/migration.md](docs/migration.md).
- New dependencies follow [DEPENDENCY_POLICY.md](DEPENDENCY_POLICY.md).
- Disclose AI assistance (see [AI Policy](#ai-policy)).
- One maintainer approval is required to merge.

### Commit Messages and PR Descriptions

- Write the subject in the imperative mood and sentence case, describing the behavior change, for
  example `Decode any percent-encoded byte in non-base64 data URLs`. A Conventional Commits prefix
  (`fix:`, `test:`, `docs:`, `refactor:`, `chore:`) is recommended.
- Explain **why** in the body: the root cause, the relevant spec or RFC section, and how the change
  addresses it.
- Link the issue the PR addresses (`Fixes #123`).

## Security

Report vulnerabilities privately through GitHub Security Advisories, as described in
[SECURITY.md](SECURITY.md). Don't report them in public issues, discussions, or pull requests.
